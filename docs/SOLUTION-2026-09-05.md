# FlashGuard: proposed solution for 5–30 Hz, low latency, and no visible trails

Reviewed 2026-09-05. `origin/test` was fetched and matches local HEAD
`c8a6386f535ac8be059ac2a821768a5c23cf9321` (Add coarse low-latency protection path).
Existing uncommitted changes in `src/FlashGuard.cpp` were inspected and preserved.
This is a source and experiment review, not a newly measured implementation.

## Recommendation

Build a GPU detector that keeps frequency history on tracked surfaces/regions,
and a cheap compositor that modifies only the current source image inside the
current region. Keep NVIDIA optical flow as an interchangeable correspondence
backend until comparable measurements establish whether it should be replaced.

The necessary change is ownership of temporal state. An object needs enough
history to establish flashing, but that history must not keep modifying the
background after the object moves. Removing old RGB is insufficient: a stale
mask applied to new RGB still produces a visible trail. The repository has
already demonstrated this failure in its risk-only architectures.

This is the most defensible next architecture from the available evidence. It
has not yet demonstrated all three requirements. Perfect classification of
arbitrary captured imagery, zero observation delay, and perfect preservation
cannot all be guaranteed; ambiguous correspondence and the first flash require
an explicit protection policy.

## Proposed processing path

```text
new captured source + capture timestamp
    → GPU multiscale luminance/chroma/structure features
    → current surface correspondence + current region support + uncertainty
    → per-surface transition timestamps, phase history, frequency confidence
    → current-region luminance/chroma envelope
    → one full-resolution current-frame composite
    → present
```

### 1. Separate geometry from brightness change

Estimate correspondence with structure features such as Census descriptors,
normalized gradients, and boundary agreement, then measure luminance/chroma
change using the original linear-light samples at corresponding locations.
Normalizing brightness for correspondence must not normalize away the flash
measurement. Research on illumination-robust alignment supports evaluating
Census; applying it successfully to this workload remains an experiment.
[Microsoft Research](https://www.microsoft.com/en-us/research/publication/illumination-change-robustness-in-direct-visual-slam/)

Start with a bounded multiscale GPU matcher and refine only uncertain boundaries
or candidate regions. Retain a high-resolution candidate path so small flashes
do not disappear in the 128×72 analysis. NVOFA should output the same geometry
contract as the portable matcher: predecessor, confidence, and consistency.
Do not let either backend directly decide “safe.”

Flat objects, contrast inversions, complete disappearance against the background,
and occlusion need separate handling. Use region boundary motion and a bounded
bank of previous phase appearances to reconnect a returning flashing object.
Identity can remain dormant while an object is invisible; a dormant identity
must not paint its last screen location. If current support cannot be established,
use a separately defined conservative regional/global fallback and measure its
distortion. This ambiguity is a real limitation, not something a decay constant
or a more expensive flow model automatically resolves.

### 2. Give frequency memory a surface owner

Keep a bounded GPU state record with identity/generation, correspondence
confidence, last positive and negative transition times, several recent periods,
phase extrema, red/chroma evidence, and protection-envelope parameters.

- A stationary region has a zero-displacement track; a moving region uses its
  validated predecessor. Both use the same frequency detector.
- Estimate full periods from successive same-polarity transitions. Opposite
  transitions validate alternating phases; do not assume a 50% duty cycle.
- Use actual capture timestamps. Duplicate/idle rendering must not manufacture
  new observations, and capture gaps must reduce confidence.
- Use hysteresis and a minimum amplitude/noise test. Maintain an optional small
  band-energy estimator for smooth oscillations without requiring a large FFT
  buffer. Neither estimator should delay presentation of the current frame.
- Keep first-event protection separate from frequency confirmation. A strong
  first transition can trigger provisional attenuation immediately; calling it
  a confirmed 5–30 Hz sequence must wait for evidence.
- Release or transport display authority according to current ownership.
  Same-coordinate similarity alone cannot restore an old object's state onto
  newly exposed background. Do not bilinearly blend identities across edges.

Retain a separate broad/red/pattern hazard path. Motion alone cannot authorize
bypass: moving high-contrast patterns can still be problematic.

### 3. Modify current pixels without recursive image blending

For validated current region support, use a stable linear-light mapping such as

`Yout(x,t) = b(track,t) + g(track,t) * (Ysource(x,t) - b(track,t))`

with `0 ≤ g ≤ 1`. For fixed `b` and `g`, temporal luminance amplitude within
that track scales by `g`. Estimate an envelope from observed phase extrema;
stabilize changes in `b` and `g`, since changing the protection itself can create
a new flash. Measure activation and release as part of output modulation.
Use independent chroma/red suppression; luminance-only control is insufficient.

Apply this transform only to current supported pixels. At a verified vacated
pixel, output the current background immediately, relative to the configured
static tone-map baseline. No previous displayed RGB is sampled. No stale
screen-space risk controls that background. Small boundary feathering must be
clipped to current support and tested for leakage.

The compositor can therefore be cheap; tracking quality becomes the principal
remaining source of localized distortion. This design removes the old recursive
trail mechanism but does not prove perfect masks or zero visible artifacts.

## Latency and frequency limits

Distinguish processing cost, capture-to-display delay, and observation time.
At 5 Hz a complete period is 200 ms; at 30 Hz it is 33.333 ms. A causal detector
cannot identify the frequency from the first isolated transition. Two same-sign
edges establish one candidate period; robust confirmation may take longer.
Immediate provisional attenuation avoids adding that observation window to the
presentation queue, at the cost of some false positives.

30 Hz at 60 samples/second is at the Nyquist boundary and phase-sensitive.
A sampled sinusoid can disappear at a particular phase. Test at 120/144/240 Hz
as well as 60 Hz, with dropped frames and variable timing. The relevant rate is
the distinct captured source rate, not the overlay's render-loop FPS. Sampling
cannot recover a transition absent from every captured sample.

Keep the existing waitable swap chain and freshest-frame policy. Add nonblocking
GPU timestamp/disjoint queries around analysis and composition, read several
frames later. Keep the NVOFA host-call duration separately; use GPU/ETW tracing
for optical-flow dependencies rather than assuming graphics timestamps isolate
another engine's execution. Report p50/p95/p99 under game GPU load, not just idle
averages. [D3D11 query documentation](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/ne-d3d11-d3d11_query)

Use PresentMon/ETW for presentation behavior and a camera/photodiode test for
physical latency. A source marker and its protected output must be correlated;
an overlay FPS counter is insufficient.
[PresentMon](https://github.com/GameTechDev/PresentMon)

NVOFA is a dedicated accelerator, but configuration trades accuracy against
performance and NVIDIA's published throughput is not this application's
end-to-end latency. Compare normal NVOFA, lite NVOFA, and the portable matcher
with the SAME detector/compositor and identical replay inputs before choosing.
[NVOFA application note](https://docs.nvidia.com/video-technologies/optical-flow-sdk/nvofa-application-note/index.html)

Desktop Duplication provides already rendered desktop images. A capture overlay
does not itself establish that every original application frame is intercepted
before any scanout. For the strongest guarantee and lowest added delay, the
long-term path is filtering inside a cooperating renderer/player before Present.
Keep the desktop overlay as the broad-compatibility path and measure its actual
exposure/timing behavior. Renderer integration is a separate deployment project.
[Microsoft Desktop Duplication](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/desktop-duplication-api)

## Implementation and acceptance order

1. Expose a shared pipeline/backend configuration to replay and live use. Record
   effective configuration, binary/source hashes, hardware, driver, timestamps,
   and reset policy. Make repeated controls agree before further tuning.
2. Add GPU/presentation profiling and capture-gap metrics. Establish optimized
   baseline cost for existing NVOFA, lite, and coarse paths at actual monitor
   resolution, with representative GPU load.
3. Add synthetic ground-truth surface IDs, support masks, and motion as an oracle
   backend. Test the frequency detector and current-frame envelope using this
   oracle first. This separates a bad mitigation design from bad tracking.
4. Replace oracle correspondence with the bounded structural matcher, then
   NVOFA under the same interface. Attribute false positives, missed flashes,
   and trails to geometry, state ownership, or envelope changes independently.
5. Run full canonical and native-resolution tests. Cover stationary/moving
   5/7.5/10/12/15/20/25/30 Hz, weak modulation, red and isoluminant color changes,
   multiple simultaneous objects, non-50% duty cycles, rotation, scale, occlusion,
   disappearance, pans, textured scrolling, scene cuts, irregular flashes,
   onset/offset, and just-outside-band controls. Out-of-band does not mean safe.
6. Measure detection delay, frequency error/confidence, moving-object attenuation,
   missed area, false-positive area, final-output flash transitions, and vacated
   pixel error together. Add a much stricter no-trail gate: exact oracle-background
   recovery on the first vacated frame, then a proposed real-tracker target of
   ≤1 display-code error at vacated pixels relative to static baseline, with
   peak/error-area reporting. Treat this as an engineering target requiring
   visual validation, not a clinical threshold. Do not accept a candidate merely
   because it clears below 5% after 70 ms.

## Intended benefit and claim boundary

The user selected 5–30 Hz. That is a useful core target: the Epilepsy Foundation
identifies that range as particularly likely to trigger photosensitive seizures.
Susceptibility also depends on brightness, contrast, color, pattern, and visual
field; people vary. FlashGuard should be described as reducing visually provoked
risk, not protecting all people with epilepsy or making arbitrary imagery safe.
Independent clinical/accessibility evaluation is needed before stronger claims.
[Epilepsy Foundation](https://go.epilepsy.com/what-is-epilepsy/seizure-triggers/photosensitivity)

The immediate decision is to stop treating flow replacement or another lifetime
sweep as the complete solution. Establish replay/live parity, measure the actual
critical path, and validate surface-owned frequency state plus current-pixel
mitigation with oracle geometry before investing in another motion backend.
